## 1. 프로젝트 개요

QuestBoard는 IT·게임 분야의 공모전, 지원사업, 해커톤, 행사, 교육 공고를 13개 출처에서 모아 보여주는 **정적 웹사이트**입니다.

```text
GitHub Actions (cron: 1시간/6시간/매일)
  └─ Python pipeline: 수집 → 정규화·분류 → 중복 병합 → 수동 YAML 반영 → 변경 이력 → JSON 생성
       └─ public/data/*.json 자동 커밋
            └─ Vite 빌드 → GitHub Pages 배포
                 └─ React SPA (검색·필터·정렬) + Firebase(Google 로그인, Firestore 개인 데이터)
```

현재 데이터 규모(2026-09-29 생성분): 공개 176건, 날짜 미상 30건, 최근 마감 83건, 검토 큐 41건. 출처 13곳 중 12곳 성공, 기업마당(`bizinfo`) 1곳 실패.

## 2. 좋은 점

### 2.1 아키텍처
- **서버 없는 구조로 운영비가 거의 들지 않습니다.** 수집은 GitHub Actions, 호스팅은 Pages, 개인 기능만 Firebase Spark를 씁니다. 개인 프로젝트로 오래 운영하기 좋은 구성입니다.
- **수집과 표시가 JSON 계약으로 분리되어 있습니다.** `schemas/opportunities.schema.json`과 `pipeline/validate.py`가 계약 역할을 하므로 프론트와 파이프라인을 따로 고칠 수 있습니다.
- **출처 하나가 실패해도 나머지는 계속 실행됩니다.** `runner.py`는 실패한 출처의 이전 정상 데이터를 그대로 유지합니다. 크롤러가 자주 깨지는 이 도메인에서 꼭 필요한 설계입니다.
- **수집 주기를 출처별로 나눴습니다.** fast(1시간)/slow(6시간)/all(매일)로 나눠 호출량과 신선도의 균형을 맞췄습니다.

### 2.2 데이터 품질
- **분류 점수가 설명 가능합니다.** `relevance.reasons`에 점수 근거가 남고, 50~69점은 검토 큐로 보내는 3단계 판정(공개/검토/제외)이 합리적입니다.
- **중복 병합 규칙이 다층적입니다.** ID → 원문 URL → 신청 URL → dedupe_key → 제목 유사도(0.90)+마감일 근접(±1일) 순으로 비교하고, 병합할 때는 우선순위가 높은 공식 출처를 대표로 씁니다.
- **변경 감지 이력이 안정적입니다.** `history.py`는 안정 ID를 먼저 매칭한 뒤 약한 키로 넘어가고, 중요 필드가 바뀌었을 때만 `UPDATED`를 붙입니다.
- **수동 개입 경로가 잘 정리되어 있습니다.** `manual/opportunities.yml`, `overrides.yml`, `exclusions.yml`로 추가·수정·제외를 코드 수정 없이 처리합니다.
- **날짜를 지어내지 않습니다.** `date_kind`(exact/ongoing/first_come/budget/unknown/inquiry)로 불확실성을 표현하고, 날짜를 모르는 공고는 별도 화면으로 분리합니다.

### 2.3 운영·윤리
- robots/약관 확인, CAPTCHA·로그인 우회 금지, 403/429 발생 시 중단 같은 **수집 정책이 문서로 명시**되어 있습니다(`docs/COLLECTORS.md`, `docs/OPERATIONS.md`).
- 구조가 바뀌어 결과가 0건이면 성공이 아니라 **구조 오류로 기록**합니다. 조용히 데이터가 비는 상황을 막아 줍니다.
- 수집 상태 페이지에서 출처별 성공/실패, 연속 실패 횟수, stale 여부를 바로 볼 수 있습니다.

### 2.4 프론트엔드·개발 환경
- 필터·정렬·페이지가 **URL 쿼리에 저장**되어 링크로 공유할 수 있고, 새로고침해도 유지됩니다.
- 다크 모드, 모바일 카드 레이아웃, `aria-*` 속성 등 기본 접근성을 챙겼습니다.
- 로그인 전에 로컬에 찜해 둔 항목을 계정으로 옮기는 마이그레이션 흐름이 있습니다.
- pytest(39개 테스트), Vitest, Playwright E2E, ESLint, `tsc`가 CI에서 모두 실행됩니다.
- Python 의존성이 PyYAML 하나뿐이고 HTTP는 표준 라이브러리로 처리해서 공급망 위험이 작습니다.

### 🔴 3.1 공개 JSON에 원문 본문이 그대로 포함됨
- `normalize.py`가 `classification_inputs=[asdict(raw)]`로 원본 수집 데이터를 통째로 저장하고, 여기에 상세 페이지 본문 `body_text`(최대 6,000자)가 들어 있습니다.
- 확인 결과 `active.json`의 **176건 전부**가 `body_text`를 포함하고, 이 필드만 약 275KB(파일 820KB의 약 1/3)를 차지합니다.
- README와 OPERATIONS 문서는 "원문 본문은 재배포하지 않는다"고 명시하고 있어서, **문서화된 정책과 실제 동작이 다릅니다.** 저작권·약관 측면에서 가장 먼저 고쳐야 할 항목입니다.
- **개선안**: 공개 JSON을 쓸 때 `classification_inputs`를 빼거나, 필요하면 해시나 출처 분류명(`original_category`)만 남깁니다. 공개 대상이 아닌 디버깅 데이터는 Actions 아티팩트로 분리합니다. `validate.py`에 "`body_text`가 포함되면 실패" 규칙을 추가해 다시 생기지 않게 막습니다.
- ✅ **처리 완료**
  - `classification_inputs`를 어디서도 다시 읽지 않는 것을 확인하고 `Opportunity` 모델과 `normalize.py`에서 필드를 제거했습니다. 이전 JSON은 `clone_opportunity`가 모르는 키를 무시하므로 그대로 읽힙니다.
  - `validate.py`와 JSON 스키마에 `classification_inputs`·`body_text`가 공개 항목에 있으면 실패하는 규칙을 추가했습니다.
  - 현재 `public/data` 4개 파일에서 해당 필드를 제거했습니다. 전체 크기가 **1.9MB → 880KB**로 줄었습니다.
  - 테스트: 정규화 결과에 본문이 없는지, 검증기가 본문 필드를 거부하는지 확인합니다. 출처를 선택하지 않은 오프라인 파이프라인 실행(읽기 → 이력 병합 → 쓰기)도 통과했습니다.
- **남은 일**: 과거 Git 커밋에는 본문이 남아 있습니다. 지우려면 이력 재작성과 강제 push가 필요하므로 별도로 결정해야 합니다(3.5와 함께 검토).

### 🟠 3.4 상세 페이지 날짜 추출이 부정확할 수 있음
- 범용 수집기(`collectors/html.py`의 `dates_from_text`)는 **본문 전체에서 처음 나오는 날짜 두 개**를 시작일/마감일로 씁니다. 게시일, 행사일, 공지 수정일이 먼저 나오면 엉뚱한 날짜가 들어갑니다.
- `onoffmix`, `dacon`, `momo365`가 이 범용 수집기를 씁니다.
- **개선안**: "접수기간", "모집기간", "마감" 같은 라벨 근처의 날짜를 우선 사용합니다. 기간이 비정상이면(예: 시작 > 마감, 기간 1년 초과) `unknown`으로 처리하고, 출처별 전용 수집기를 늘립니다.
- ✅ **처리 완료**
  - `recruit_dates_from_text`를 추가해 범용 수집기의 상세 페이지에만 적용했습니다. 접수·모집·신청·응모·공모·제출 기간이나 마감 라벨 뒤 80자 안의 날짜를 먼저 쓰고, `2026.12.20 ~ 01.10`처럼 연도가 빠진 마감일은 연도를 넘겨 해석합니다. 라벨 뒤에 날짜가 하나만 있으면 마감일로 봅니다.

  - 다른 전용 수집기가 쓰는 `dates_from_text`는 이미 기간 칸만 넘겨받으므로 동작을 바꾸지 않았습니다.
  - 실사이트 확인: 모모365 상세 페이지는 `등록일 2026-10-06 마감일 2026-10-31` 형태라, 기존 로직은 **등록일을 접수 시작일로 잘못 넣고 있었습니다**(10건 모두). 새 로직은 마감일만 정확히 추출합니다. DACON 12건은 결과가 같았습니다.

### 🟠 3.5 저장소 비대화
- 커밋 924개 중 914개가 데이터 자동 커밋이고 `.git`은 이미 61MB입니다. 매시간 약 1.6MB짜리 JSON이 바뀌므로 계속 커집니다.
- **개선안**:
  - 3.1에서 `classification_inputs`를 빼면 파일 크기가 약 1/3 줄어듭니다.
  - JSON을 `indent=2` 대신 압축 형식으로 쓰거나, 데이터만 별도 브랜치(`data`)나 Release 자산에 올립니다.
  - 데이터가 바뀌지 않은 실행은 이미 커밋을 건너뛰고 있지만, `generated_at`만 바뀐 경우도 건너뛰도록 비교 기준을 조정합니다.
- ✅ **해소 (2차)**: 3.1로 데이터 파일이 절반 이하가 되었고, 자동 수집을 하루 한 번으로 바꾸면서 데이터 커밋도 하루 약 30회에서 1회로 줄었습니다. 저장소 증가 속도는 이전의 약 1/60 수준입니다.

- **남은 일(결정 필요)**: 이미 커진 과거 이력(원문 본문 포함)을 정리할지는 이력 재작성과 강제 push가 필요해서 결정이 필요합니다.

### 🟠 3.8 HTTP 클라이언트의 예의(politeness) 장치 부족
- 재시도와 지수 백오프는 있지만, robots.txt 자동 확인, 호스트별 최소 요청 간격, `Retry-After` 존중, 조건부 요청(ETag/If-Modified-Since)은 없습니다. 상세 요청 사이 대기도 0.15초로 짧습니다.
- User-Agent의 연락처가 `https://github.com/`로만 되어 있어 운영자를 알 수 없습니다.
- **개선안**: `urllib.robotparser`로 실행마다 한 번 확인하고, 호스트별 요청 간격을 1초 이상으로 늘립니다. UA에는 실제 저장소 URL을 넣습니다.
- ✅ **처리 완료**
  - robots.txt를 호스트별로 실행당 한 번 읽어 `QuestBoard` 에이전트 기준으로 확인합니다. RFC 9309에 따라 4xx면 허용하고, 5xx·접속 실패면 전체 금지로 봅니다. 금지된 URL은 요청하지 않고 `RobotsDisallowed` 오류로 출처 실패를 기록합니다.
  - 범용 수집기가 상세 페이지 오류를 삼키고 "원문 확인 필요" 대체 항목을 만들던 경로에서도 robots 금지는 다시 던지게 해, 금지된 URL이 공개 데이터에 들어가지 않게 했습니다.
  - 같은 호스트에는 최소 1초 간격으로 요청합니다(`Crawl-delay`가 더 길면 그 값). 수집기마다 흩어져 있던 0.1~0.15초 `sleep`은 제거했습니다.
  - 429·503의 `Retry-After`가 30초 이하면 기다렸다가 재시도하고, 그보다 길면 재시도하지 않습니다.
  - User-Agent 연락처를 `https://github.com/bluepet032/QuestBoard`로 바꿨습니다.
  - 테스트 5개(`urlopen` 모킹)를 추가했습니다. 13개 출처의 robots.txt를 직접 확인한 결과는 3.14에 정리했습니다.
- **영향**: 상세 페이지를 많이 읽는 출처는 요청당 약 1초씩 수집 시간이 늘어납니다. 출처당 최대 150건 기준으로 몇 분 수준입니다.

### 🟠 3.9 자동 커밋 push 충돌 가능성
- `collect.yml`은 체크아웃 후 수집에 몇 분이 걸리는데 `git push` 전에 rebase를 하지 않습니다. 그 사이 사람이 `main`에 push하면 수집 결과 push가 거부되고 배포가 실패합니다.
- **개선안**: push 전에 `git pull --rebase` 후 재시도하는 로직을 넣습니다(데이터 경로만 바뀌므로 충돌 가능성은 낮습니다).
- ✅ **처리 완료**: push 전에 `git pull --rebase`를 하고, 실패하면 rebase를 중단한 뒤 10·20초 간격으로 최대 3번 재시도합니다. 모두 실패하면 오류로 끝납니다.
- **확인 필요**: Actions에서만 실행되는 부분이라, 커밋 후 첫 자동 수집 실행 로그로 확인해야 합니다.

### 🟢 3.11 Firestore 규칙에 스키마 검증이 없음
- `users/{uid}` 하위 문서는 본인이면 아무 필드나 크기 제한 없이 쓸 수 있습니다. 보안 사고는 아니지만, 버그나 악의적 클라이언트가 무료 사용량을 소진할 수 있습니다.
- **개선안**: 키워드 길이, 문서 필드 목록, 문자열 최대 길이를 규칙에서 검증합니다.
- ✅ **규칙 작성 (2차)**: `firestore.rules`를 사이트가 실제로 쓰는 필드와 길이만 허용하도록 바꿨습니다.
  - 찜: `item`, `remindersEnabled`, `resultDate`(10자), `note`(500자), `updatedAt`만 허용. 수정은 알림 설정·발표일·메모만 가능
  - 키워드: 1~60자, 생성·삭제만 가능(수정 불가)
  - 알림: 정해진 8개 필드와 `schedule`·`keyword` 유형만 허용. 수정은 "읽음" 표시만 가능
  - 사용자 문서(`users/{uid}`): 읽기·삭제만 가능(사이트가 쓰지 않음)
  - 코드의 모든 쓰기 경로(`src/personal.tsx`, `src/account.tsx`)와 하나씩 대조했습니다. 성공해야 하는 쓰기 9개와 거부해야 하는 쓰기 11개를 검사하는 스크립트를 `tests/firestore/rules.test.mjs`에 넣었습니다.
- ⚠ **에뮬레이터 검증은 이 PC에서 끝내지 못했습니다.** 최신 Firebase CLI는 JDK 21이 필요한데 이 PC에는 JDK 11만 있고, C 드라이브 공간도 부족했습니다.
- **남은 일(도움 필요)**: `docs/DEPLOYMENT.md`의 "보안 규칙 검사"대로 확인한 뒤 Firebase 콘솔에 게시해 주세요. 검사 없이 게시했는데 찜·키워드 저장이 실패하면, 콘솔의 규칙 기록에서 이전 버전으로 바로 되돌릴 수 있습니다.

### 🔴 3.14 온오프믹스 robots.txt가 수집을 금지함 (작업 중 새로 발견)

- **남은 일(결정 필요)**: 프로젝트 정책상 `config/sources.yml`에서 `enabled: false`로 비활성화하는 것이 맞아 보입니다. 비활성화하면 다음 실행부터 온오프믹스에서만 온 공고가 빠집니다. 출처 목록이 바뀌는 일이라 직접 정하실 수 있게 남겨 두었습니다.
